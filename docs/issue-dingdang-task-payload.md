# 问题单：叮当派发任务时未传递节点任务内容（dataItems 仅为占位说明）

**提交方**：研枢科研智能体集群（8 个 agent，AIC 前缀 `1.2.156.3088.1.BUPT.VTF97R.*`）
**平台**：https://wt.ioa.pub/
**日期**：2026-10-11
**影响**：叮当每次调用我们的 partner，节点都收不到自己该做什么，必须由用户**重复说明**才能推进

---

## 一、问题描述

叮当完成协作规划、按 DAG 向我们的 agent 派发 `start` 命令时，
`dataItems` 里只有「**用户原话 + 一段固定占位说明**」，
**没有该 DAG 节点的任务参数，也没有上游节点的产物**。

结果是：无状态的 partner 收到任务后无法执行，只能反过来向用户追问缺失信息，
用户被迫把同一件事再讲一遍。

## 二、实测证据

对 8 个 agent 的入站任务库做了全量统计（脚本：`acps_cluster/deploy/discovery_diagnostics/analyze_payload_shape.py`，只读）：

**共检查入站 `start` 命令 315 条，按发送方分组：**

| 发送方 | 条数 | 其中带占位符 |
|---|---|---|
| 叮当（`…0001.00001.EZTK03.JISTB6.0P3V`） | 66 | **52（79%）** |
| 我们自己（leader `…VTF97R.JXN8O8.98DOO8.0EB6`） | 127 | 0（0%） |
| 其他 | 122 | 0（0%） |

**叮当发来的 payload 长度上限仅 1288 字符；我们自己委派的同类任务最长 26176 字符**
（我们把自己那一侧的完整指令放进了 `dataItems[].text`，所以链路本身是通的）。

### 2.1 叮当派发给 Writer 的原始 start 命令（完整未删减）

```json
{
  "type": "task-command",
  "id": "cmd-197e1304-a28d-4241-9196-97f570bccc7e",
  "sentAt": "2026-10-11T09:10:07.997012+00:00",
  "senderRole": "leader",
  "senderId": "1.2.156.3088.1.0001.00001.EZTK03.JISTB6.0P3V",
  "command": "start",
  "taskId": "6626ca9a-3dcc-415d-adf3-3e1f36052302",
  "sessionId": "session_2073",
  "dataItems": [
    {
      "type": "text",
      "text": "我说的是研枢partner\n\nDAG 指定的上游产物摘要：\n叮当已完成协作规划并开始按 DAG 派发。"
    }
  ]
}
```

其中：
- `"我说的是研枢partner"` = **用户原话**（叮当把用户消息原样转给了所有节点）；
- `"\n\nDAG 指定的上游产物摘要：\n叮当已完成协作规划并开始按 DAG 派发。"` = **固定模板文字**，
  **没有任何实际的上游产物**。

### 2.2 叮当派发给 Scout 的 start 命令（同类形态）

```json
{
  "senderId": "1.2.156.3088.1.0001.00001.EZTK03.JISTB6.0P3V",
  "command": "start",
  "sessionId": "session_2073",
  "dataItems": [
    {"type": "text",
     "text": "研枢scout\n\nDAG 指定的上游产物摘要：\n叮当已完成协作规划并开始按 DAG 派发。"}
  ]
}
```

同一次会话里，叮当把**同一条用户消息**派发给了不同角色的节点（scout / writer），
没有按节点区分任务内容。

### 2.3 start 命令的字段集合（66 条完全一致，没有承载节点信息的字段）

```
['command', 'dataItems', 'id', 'senderId', 'senderRole', 'sentAt', 'sessionId', 'taskId', 'type']
```

即：**协议里没有可承载「本节点任务参数」或「上游产物」的字段**，
唯一的内容通道 `dataItems` 里放的是用户原话 + 占位符。

### 2.4 造成的实际后果（同一次会话 `session_2073`）

1. 叮当派发 → Writer 节点收到的只有 `"我说的是研枢partner"` + 占位符；
2. Writer 无法开始，只能回复一份**追问清单**（topic / materials / 篇幅格式 / 起草模式 / 语言）；
3. 用户补充 `"写一篇3000字的difussion综述"`；
4. 叮当再次派发，这次 payload 变成
   `"我说的是研枢partner\n\n上一轮候选结果：\n<Writer 的追问全文>\n用户回答：写一篇3000字的difussion综述\n\nDAG 指定的上游产物摘要：…"`
   —— 即**靠把整段对话历史拼进用户消息**才勉强把信息带到（该包 601 字符，是 66 包里少数不含占位符的之一）。

也就是说：目前只能靠"多轮追问 + 把历史拼进用户消息"绕过，**用户每换一个任务都要重复一轮**。

## 三、期望行为

叮当在派发 DAG 节点时，把**该节点的输入**放进 `dataItems`（或新增专用字段），至少包含：

1. **本节点的任务参数**：叮当规划该节点时已经决定的内容
   （例如 Writer 节点的 topic / 目标字数 / 语言 / 模式；Scout 节点的检索主题与篇数上限）；
2. **上游节点的产物**：`DAG 指定的上游产物摘要` 这一句应替换为**实际的上游产物内容或摘要**
   （当前是固定模板文字，与"摘要"二字不符）；
3. **节点在 DAG 中的位置**（可选）：便于节点知道自己是第几步、还需要等谁。

参考：我们自己这一侧的委派是把**完整指令**写入 `dataItems[].text`（最长 26176 字符），
节点因此能一次执行到位——说明该通道本身完全支持长内容。

## 四、复现方式

```bash
# 在仓库根目录、保存有任务库的一侧执行（只读）
python3 acps_cluster/deploy/discovery_diagnostics/analyze_payload_shape.py
```

或直接查某次派发：

```sql
SELECT command_history FROM aip_tasks
WHERE direction='inbound' ORDER BY created_at DESC LIMIT 5;
-- 取 command_history 里 command='start' 的那条，看 dataItems[0].text
```

对照要点：`senderId` 以 `1.2.156.3088.1.0001.00001.EZTK03.` 开头 = 叮当；
统计 `dataItems[].text` 里是否含固定串 `叮当已完成协作规划并开始按 DAG 派发`。

## 五、补充说明（不是我们的问题，供定位参考）

- 我们的 agent 在准入与执行两侧均正常工作：给**我们自己**的委派（127 条，含完整指令）
  全部正常执行完成；叮当发来的**内容完整**的包（14 条）也能正常执行。
- 因此本问题**仅**由"派发时未携带节点任务内容"造成，与 agent 侧无关。

## 六、临时绕过（我们这侧，供参考）

当前用户可用的绕过方式：**把完整任务写进第一条消息**（越具体越好），
并接受多一轮追问——但这正是本问题单希望消除的重复成本。
